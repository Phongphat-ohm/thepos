# รายงานตรวจ Web portal ก่อนแก้โค้ด

วันที่ 21 พฤศจิกายน 2026 ตรวจจาก working tree ปัจจุบันของ ThePOS ซึ่งมีงานปรับโครงสร้างค้างอยู่แล้ว รอบนี้เพิ่มเฉพาะรายงานและหลักฐานทดสอบ ไม่แก้โค้ดผลิตภัณฑ์ API ชนิดข้อมูล หรือข้อมูลร้านจริง

พบปัญหาหลัก 4 กลุ่มที่ควรแก้ก่อนรับรองการใช้งาน ได้แก่ หน้าตรวจนับสต็อกที่เข้าไม่ได้ การค้นหาสินค้าและสมาชิกที่ย้อนกลับไปใช้คำเดิม การแสดงข้อมูลเก่าหลังโหลดล้มเหลว และลำดับข้อมูลในไฟล์ส่งออกไม่ตรงกับหน้าจอ การคำนวณยอดกับ PostgreSQL ยังรับรองไม่ได้ เพราะฐานข้อมูลทดสอบไม่พร้อมใช้งาน

## กติกาธุรกิจที่ยืนยันแล้ว

- Web portal ใช้ดูรายงานและจัดการหลังบ้าน ส่วนการขายผ่าน Desktop
- รับคืนสินค้าและบันทึกคืนเงินบนเว็บได้ตามสิทธิ์ผู้ใช้
- ต้องมีการตรวจนับและอนุมัติสต็อกใน Web portal
- รายงานรายวันใช้วันปฏิทินเวลาไทย และหักยอดคืนในวันที่คืน โดยไม่ย้อนเปลี่ยนวันขายเดิม
- การเข้าถึงรายงานและกำไรแยกตามสิทธิ์รายบุคคล
- Excel และ PDF ใช้ตัวกรองและช่วงวันที่เดียวกับรายงาน และต้องแจ้งเมื่อข้อมูลถูกจำกัดจำนวน

## ปัญหาที่ควรแก้ก่อนใช้งาน

### 1 หน้าตรวจนับและอนุมัติสต็อกยังเปิดจากเว็บไม่ได้

**ระดับ P1 — ยืนยันจากโครงสร้างเส้นทางและข้อกำหนดที่เจ้าของระบบยืนยัน**

มี `StockCountsWorkspace` ซึ่งรองรับกรอกผลนับ ดูใบตรวจนับ และอนุมัติตามสิทธิ์ แต่ `App` และรายการเส้นทางเว็บไม่มีหน้าดังกล่าว หน้าล็อตสินค้าที่เข้าถึงได้ส่ง `count={false}` เสมอ จึงใช้บันทึกผลนับไม่ได้ ผู้ใช้ที่มีสิทธิ์ตรวจนับหรืออนุมัติไม่สามารถทำงานครบขั้นตอนผ่านเมนูเว็บ

หลักฐาน: [หน้าตรวจนับที่มีอยู่](D:/.PHONGPHAT/thepos/web-portal/src/ui/features/stock-counts/workspace.tsx:12), [เส้นทางเมนู](D:/.PHONGPHAT/thepos/web-portal/src/ui/components/layout/navigation.ts:29), [หน้าคลังที่ปิดการกรอกผลนับ](D:/.PHONGPHAT/thepos/web-portal/src/ui/features/inventory/workspace.tsx:42), [API ตรวจนับและอนุมัติ](D:/.PHONGPHAT/thepos/apps/server/src/modules/stock-counts/routes.ts:18)

แนวทางแก้: เชื่อมหน้าตรวจนับและใบตรวจนับเข้ากับเมนูและ App โดยใช้ `inventory:count` สำหรับส่งผลนับ `inventory:read` สำหรับดูใบ และ `inventory:approve` สำหรับอนุมัติหรือปฏิเสธ ใช้ API ที่มีอยู่ก่อนพิจารณาเพิ่ม interface

วิธีตรวจรับ: พนักงานคลังส่งผลนับได้ ผู้จัดการอนุมัติหรือปฏิเสธได้ บัญชีไม่มีสิทธิ์เรียกทั้งหน้าและ API ไม่ได้ และการอนุมัติต้องปรับยอดเพียงครั้งเดียว การตรวจฐานข้อมูลจริงของกรณีนี้ยังรอ PostgreSQL ทดสอบ

### 2 ค้นหาจากหน้าที่สองแล้วกลับไปแสดงคำค้นเดิม

**ระดับ P1 — ทำซ้ำได้ในเบราว์เซอร์ทั้งหน้าสินค้าและสมาชิก ด้วย API จำลอง**

ขั้นตอน: เปิดรายการ → ไปหน้าที่ 2 → พิมพ์ `NEW` → กดค้นหา ผลที่พบคือช่องค้นหาเป็น `NEW` แต่รายการยังเป็น “สินค้า เดิม” หรือ “สมาชิก เดิม” ทั้งที่ API ตอบสำเร็จ

ตัวอย่างคำขอที่บันทึกได้:

```text
GET catalog/products?q=NEW&page=1&limit=25&sortBy=name&sortDir=asc
GET catalog/products?q=&page=1&limit=25&sortBy=name&sortDir=asc
```

การกดค้นหาเรียกโหลดคำใหม่โดยตรง พร้อมเปลี่ยนเลขหน้าเป็น 1 จากนั้น effect โหลดอีกครั้งด้วยคำเก่าซึ่งยังไม่ถูกอัปเดต กลไกหมายเลขคำขอทำให้คำขอเก่าที่เริ่มทีหลังชนะ ผลลัพธ์จึงไม่ตรงกับคำค้นและอาจนำไปสู่การเปิดหรือแก้ไขรายการผิด

### 3 โหลดล้มเหลวแล้วยังแสดงข้อมูลเดิมพร้อมสถานะใหม่

**ระดับ P1 — ทำซ้ำได้ในเบราว์เซอร์ ด้วย API จำลอง**

หน้ารายงาน: โหลดสำเร็จแล้วกดเรียงคอลัมน์ “ขาย (บาท)” โดยให้คำขอใหม่ตอบ 503 พบข้อความผิดพลาด แต่ตารางเดิมยังอยู่ ลูกศรเปลี่ยนเป็นลำดับใหม่ และปุ่ม Excel กลับมากดได้หลังคำขอล้มเหลว จึงแสดงข้อมูลกับเงื่อนไขที่ยืนยันสำเร็จไม่ตรงกัน

หน้าแดชบอร์ด: โหลดสำเร็จที่ยอด 1234.50 บาท แล้วให้การรีเฟรชตอบ 503 พบยอดเดิมยังอยู่ใต้ข้อความ “ยอดขายสุทธิวันนี้” โดยไม่มีเวลาอัปเดตล่าสุดหรือป้ายว่าข้อมูลเก่า แม้มีข้อความแจ้งเชื่อมต่อไม่ได้

วิธีตรวจรับ: จำลองการเรียง เปลี่ยนหน้า รีเฟรช และเซสชันหมดอายุที่ทำให้โหลดไม่ได้ ต้องไม่แสดงว่าข้อมูลเดิมเป็นผลของคำขอใหม่ และไม่ส่งออกด้วยสถานะที่ไม่เคยโหลดสำเร็จ

### 4 Excel และ PDF ไม่ใช้ลำดับเดียวกับรายงานบนเว็บ

**ระดับ P2 — ยืนยันจากคำสั่ง SQL ที่สร้างผ่าน service จริง โดยไม่เชื่อมฐานข้อมูล**

หน้าจอส่ง `page` พร้อม `sortCol` และ `sortDir` ส่วนการส่งออกส่งตัวกรองและการเรียง แต่ไม่ส่ง `page` ฝั่งเซิร์ฟเวอร์สร้างคำสั่งเรียงตามคอลัมน์เฉพาะแขนงที่มี `input.page` ทำให้แขนงส่งออกกลับไปใช้ลำดับตั้งต้น เช่น SKU แทนยอดขาย

ตัว probe เรียก `createReports().report()` ทั้งสองแบบและจับ SQL ที่ Prisma สร้าง พบคำสั่ง `ORDER BY` ที่ผู้ใช้เลือกในแขนงแบ่งหน้า แต่ไม่พบในแขนงส่งออก หากมีมากกว่า 10000 แถว การตัดข้อมูลก่อนใช้ลำดับที่ต้องการยังอาจทำให้ได้คนละชุดกับที่ผู้ใช้คาดหวัง

แนวทางแก้: ใช้การสร้างลำดับเดียวกันทั้งแขนงแบ่งหน้าและส่งออก และกำหนดตัวตัดสินเมื่อค่าเท่ากันเพื่อให้แบ่งหน้าคงที่ โดยไม่ต้องเพิ่ม public API เพราะ query รองรับการเรียงอยู่แล้ว

วิธีตรวจรับ: เทียบข้อมูลทุกหน้ากับ Excel และ PDF โดยใช้ตัวกรองเดียวกัน ตรวจการเรียงข้อความ ตัวเลข ค่าติดลบ และค่าซ้ำ ทั้งขาขึ้นและลง รวมข้อมูลเกิน 10000 แถวที่ต้องเลือกชุดแรกตามลำดับที่ร้องขอและแจ้งการจำกัดข้อมูล

## ผลตรวจแยกตามหัวข้อ

### TypeScript และ build ของเว็บ

- `bun run --cwd web-portal typecheck` ผ่าน
- `bun run --cwd web-portal build` ผ่าน มีคำเตือนเรื่อง annotation ของ dependency และขนาด chunk ของ ExcelJS ประมาณ 936.55 kB ก่อน gzip ไม่มีข้อผิดพลาดที่ทำให้ build ล้มเหลว

### ชุดทดสอบทั่วไป

`bun run test` ผ่าน 12 ไฟล์ รวม 37 รายการ ขอบเขตนี้ไม่รวม Web portal จึงใช้ยืนยันได้เฉพาะส่วนที่ชุดทดสอบครอบคลุม

### การเชื่อมฐานข้อมูลและธุรกรรม

เรียกชุด integration ของ operations, web-portal-cors, inventory, dividends และ auth ผ่าน `bun run test:integration` แต่ทั้ง 5 suite ติดขั้นเตรียมฐานข้อมูลที่ `127.0.0.1:54329` ไม่ตอบสนอง รวม 31 รายการถูกข้าม ยังไม่ได้เริ่มทดสอบพฤติกรรม Docker daemon ไม่พร้อมเช่นกัน ไม่มีการสั่งเริ่มฐานข้อมูลหรือแก้ข้อมูลร้าน

จึงยังไม่รับรองตัวเลขจริงของรายงาน 14 ประเภท การคืนบางรายการ การกระทบยอดชำระ กำไร ปันผล หรือการบันทึกงานหลังบ้านบน PostgreSQL ต้องรันซ้ำในฐานข้อมูลแยกที่สร้างโดย `isolatedDatabase()` เมื่อบริการทดสอบพร้อม ห้ามเปลี่ยนไปใช้ฐานข้อมูลร้านแทน

### เวลาไทย การคืนสินค้า และสิทธิ์

probe ผ่าน service จริงยืนยันว่าช่วงวันที่ 31 ตุลาคม ถึง 1 พฤศจิกายน 2026 ถูกส่งเป็น UTC ตั้งแต่ `2026-10-30T17:00:00.000Z` ถึงก่อน `2026-11-01T17:00:00.000Z` และ SQL ใช้ `Asia/Bangkok` จัดกลุ่มวันกับเดือน ยอดคืนเลือกจาก `sale_returns.created_at` แยกจากเวลาขาย รวมในรายงานวิธีชำระด้วย ข้อนี้เป็นหลักฐานระดับ SQL และพารามิเตอร์ ยังไม่ใช่ผลคำนวณบนข้อมูลจริง

ทดสอบฟังก์ชันสิทธิ์จริงด้วยบัญชีจำลองแล้ว: ผู้มี `report:sales` ไม่ได้สิทธิ์กำไรโดยอัตโนมัติ อุปกรณ์เว็บถูกตัด `sales:checkout` และ `shift:operate` ส่วนสิทธิ์เขียนงานหลังบ้านยังใช้ได้ตามที่ให้ไว้ ตรวจ route พบการ authorize แยกสำหรับรายงานแต่ละชนิดและการเขียนสินค้า สต็อก สมาชิก หุ้น และตั้งค่า การทดสอบ session จริงและ CORS ยังติดฐานข้อมูลตามหัวข้อก่อนหน้า

ข้อสงสัยเรื่อง regex เรียงทศนิยมถูกตัดออกจากรายการปัญหา หลังจับ SQL ผ่าน Prisma จริงพบรูปแบบทศนิยมถูกต้องใน probe การทดสอบลำดับบน PostgreSQL ยังต้องทำภายหลัง

### Excel และ PDF

เรียก exporter จริงของเว็บใน Chromium ด้วยข้อมูลจำลอง 2 แถว ยอด `20.50` และ `-5.25` ทั้งสองไฟล์สร้างสำเร็จ Excel อ่านกลับด้วย ExcelJS ได้ค่าตัวเลข `20.5` และ `-5.25` พร้อมรูปแบบทศนิยมสองตำแหน่ง ชื่อร้าน ช่วงวันที่ และคำเตือน 10000 รายการอยู่ในไฟล์

PDF ถูกแปลงเป็น PNG ด้วย Poppler และตรวจภาพแล้ว ตัวอักษรไทย วันที่ ยอดบวก ยอดลบ คำเตือน และเลขหน้าอ่านได้ ข้อนี้ยืนยันการส่งออก fixture ขนาดเล็ก ยังไม่ใช่การเทียบยอดกับฐานข้อมูลทุกหน้า ผลส่งออกจริงยังมีปัญหาลำดับตามข้อ 4

### การโหลดผิดพลาดและเซสชัน

Chromium ใช้ API จำลองเพื่อทำซ้ำข้อ 2–3 โดยไม่เรียกข้อมูลร้านจริง ทดสอบ web transport เมื่อ access หมดอายุ พบเรียกรายงาน 2 ครั้งและ refresh 1 ครั้งก่อนสำเร็จ ส่วนกรณี refresh ตอบ 401 ส่งข้อผิดพลาด `SESSION_REQUIRED` กลับผู้เรียก ไม่มีผลสำเร็จปลอม การจัดการข้อมูลเก่าบนหน้าจอยังต้องแก้ตามข้อ 3

## ลำดับแก้และงานตรวจรับที่เหลือ

1. เชื่อมหน้าตรวจนับและอนุมัติสต็อกให้ครบสิทธิ์ พร้อมแก้การค้นหาสินค้าและสมาชิกจากหน้าที่สอง
2. แก้สถานะข้อมูลเก่าและเงื่อนไขรายงานเมื่อโหลดไม่สำเร็จ
3. ใช้ลำดับเดียวกันสำหรับรายงานและการส่งออก แล้วเพิ่มกรณีถดถอยในขั้นตอนตรวจเว็บ
4. เมื่อ PostgreSQL ทดสอบพร้อม รัน integration ที่ติดอยู่และเพิ่ม fixture ก่อน/หลังเที่ยงคืนไทย ข้ามเดือน ขาย/คืนวันเดียวกัน คืนข้ามวัน คืนบางส่วน วิธีจ่ายผสม ค่าติดลบ ตัวกรองว่าง และผลเกิน 10000 แถว ตรวจ read/write ของแต่ละบทบาทบนฐานข้อมูลแยก

เรื่องธุรกิจที่ต้องถามระหว่างตรวจได้รับคำตอบแล้ว: เว็บรับคืนเงินได้ตามสิทธิ์ และต้องมีงานตรวจนับ/อนุมัติสต็อก ส่วนการใช้ QR นับร่วมกันผ่านมือถือและการเข้าถึงจากนอก LAN ยังไม่ได้กำหนดในรอบนี้ หากจะรวมขั้นตอนนั้นต้องตกลงสภาพเครือข่ายและตรวจการเชื่อม API ของหน้ามือถือเพิ่มเติม
